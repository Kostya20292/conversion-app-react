## 3. Backend — варианты на выбор

Runtime для API и воркеров конвертации. Общее для всех вариантов Node.js-ветки: TypeScript, multipart upload, argon2, JWT в httpOnly cookie, archiver, file-type, dotenv.

Нужно выбрать **один** вариант A–D (или предложить свой).

### Вариант A. Express + TypeScript

| Плюсы                                | Минусы                                |
| ------------------------------------ | ------------------------------------- |
| Максимум примеров и туториалов       | «Сырой» каркас — больше ручной сборки |
| Простой старт, гибкий контроль       | Структура проекта на совести команды  |
| Легко стыкуется с multer, rate-limit | Нет из коробки DI / модулей           |

**Типичный набор:** Express, multer, express-rate-limit, cookie-parser, jsonwebtoken.

**Кому подходит:** учебный проект, быстрый MVP, минимум «магии» фреймворка.

---

### Вариант B. Fastify + TypeScript

| Плюсы                                       | Минусы                                                        |
| ------------------------------------------- | ------------------------------------------------------------- |
| Быстрее Express, схема валидации из коробки | Чуть меньше материалов, чем у Express                         |
| Плагины, хороший TypeScript DX              | Экосистема middleware другая (не все express-\* подходят 1:1) |
| Удобные JSON Schema / TypeBox для API       | —                                                             |

**Типичный набор:** Fastify, `@fastify/multipart`, `@fastify/rate-limit`, `@fastify/cookie`, `@fastify/jwt`.

**Кому подходит:** если хочется современный Node-API без тяжести Nest.

---

### Вариант C. NestJS + TypeScript

| Плюсы                                               | Минусы                                      |
| --------------------------------------------------- | ------------------------------------------- |
| Модули, DI, guards, pipes — структура «как в проде» | Круче порог входа, больше бойлерплейта      |
| Отлично ложится на auth, API-key guards, jobs       | Для маленького сервиса может быть избыточно |
| Встроенные паттерны под REST и документацию         | —                                           |

**Типичный набор:** NestJS, multer (через Nest), `@nestjs/throttler`, passport/jwt или cookie-сессии.

**Кому подходит:** если цель — практика «enterprise»-структуры, а не минимальный код.

---

### Вариант D. Python (FastAPI) — отдельный бэкенд

| Плюсы                                                   | Минусы                               |
| ------------------------------------------------------- | ------------------------------------ |
| Удобно для PDF/DOCX-библиотек (часть экосистемы Python) | Два языка в проекте (React + Python) |
| Быстрый REST, автодоки OpenAPI                          | Сложнее шарить типы с фронтом        |
| —                                                       | Другой деплой / окружение            |

**Кому подходит:** только если сознательно хотите Python под конвертацию документов. Для v1 обычно избыточно при LibreOffice + Node.

---

### Сводка backend

## 3.1. База данных — варианты на выбор

Сущности по ТЗ: User, ConversionBatch, ConversionJob, StoredFile, ShareLink, ApiKey.  
ORM/доступ к данным выбирается **вместе** с БД (или отдельно).

### БД: вариант 1. SQLite

| Плюсы                                     | Минусы                                   |
| ----------------------------------------- | ---------------------------------------- |
| Ноль установки сервера БД, один файл      | Слабее под высокую параллельную запись   |
| Идеально для локальной разработки и учёбы | Не тот же профиль, что «прод» с Postgres |
| Простой бэкап (скопировал файл)           | —                                        |

**Кому подходит:** v1, один инстанс приложения, локальный диск.

---

### БД: вариант 2. PostgreSQL

| Плюсы                                       | Минусы                        |
| ------------------------------------------- | ----------------------------- |
| Нормальный выбор «как в проде»              | Нужен сервер / Docker Compose |
| Надёжные транзакции, индексы, рост нагрузки | Чуть больше DevOps на старте  |
| Удобно позже вынести jobs/queue             | —                             |

**Кому подходит:** если хотите сразу привычный прод-стек или планируете деплой не на один процесс.

---

### БД: вариант 3. MongoDB

| Плюсы                                    | Минусы                                         |
| ---------------------------------------- | ---------------------------------------------- |
| Гибкие документы (batch + jobs вложенно) | Связи User ↔ files ↔ shares менее естественны  |
| Быстрый старт схем                       | Для нашей реляционной модели из ТЗ обычно хуже |

**Кому подходит:** слабо; модель в ТЗ ближе к реляционной. Оставляем как опцию «если очень хочется NoSQL».

---

### Доступ к данным (ORM / query layer)

Выбрать **один** вместе с БД:

| #   | Вариант      | С чем дружит       | Плюсы                                 | Минусы                                    |
| --- | ------------ | ------------------ | ------------------------------------- | ----------------------------------------- |
| O1  | **Prisma**   | SQLite, PostgreSQL | Удобные миграции, типы, Prisma Studio | Абстракция поверх SQL                     |
| O2  | **Drizzle**  | SQLite, PostgreSQL | Ближе к SQL, лёгкий                   | Меньше «магии», чуть больше ручной работы |
| O3  | **TypeORM**  | SQLite, PostgreSQL | Привычен в Nest-экосистеме            | Тяжелее и спорнее DX, чем Prisma/Drizzle  |
| O4  | **Mongoose** | MongoDB            | Только если выбрана Mongo             | См. минусы Mongo                          |

### Сводка БД

| Связка (пример)               | Оценка для Convertly               |
| ----------------------------- | ---------------------------------- |
| SQLite + Prisma               | Самый простой старт                |
| SQLite + Drizzle              | Простой старт, больше контроля SQL |
| PostgreSQL + Prisma           | «Прод-like», чуть больше инфры     |
| PostgreSQL + Drizzle          | То же, легче ORM                   |
| NestJS + TypeORM + PostgreSQL | Классика Nest-курсов               |
| Mongo + Mongoose              | Не рекомендуется под текущее ТЗ    |

**Зафиксировать БД:** `_____` (SQLite / PostgreSQL / MongoDB)  
**Зафиксировать ORM:** `_____` (Prisma / Drizzle / TypeORM / Mongoose)
